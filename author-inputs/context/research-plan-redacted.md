## 研究问题和范围

核心问题是：**判分程序失败后，系统能否保留失败信息，将“没有判出来”与“确实答错”区分开？采用已有修法后，这些信息能否完整到达结果接口？**

研究依次回答三个问题：失败信息在哪里丢失、现有数据在指定条件下观察到了什么、修复后选定链路是否满足预先写定的要求。

| 项目 | 最小范围 |
| --- | --- |
| 研究对象 | 固定版本的 verl 与 Math-Verify 奖励判分组合，沿用现有本机环境和固定回答，不加载模型权重 |
| 新增验证主路径 | 判分包装与进程池 → `rate_limited` 管理器 → `RewardLoopManager.compute_rm_score` 批次汇总 → `extract_reward` 奖励读取 → 一处已有结果导出接口 |
| 故障范围 | 已暴露到包装或管理器的执行失败及其附加信息；不承诺发现判分库内部已被静默吞掉的全部错误 |
| 改进范围 | 保留失败信息、保证样本与结果对应、避免稀疏字段汇总引起的异常；保持原数学判分规则和故障回退分数策略 |
| 现有其他路径 | 生成路径等已有故障记录继续作为分析材料；不据此声称新增修复已覆盖这些路径 |
| 结论边界 | 固定软件版本、平台和实验条件下的模块级结果，不外推为完整训练效果或实际部署故障率 |

毕业设计副本当前为 `d86baaa404f1b3b5b1a1fe49453075e9a82d2a0e`；已有实验分别对应各自记录的执行快照，不能用当前仓版本替代历史执行版本。核心对象为 verl PR #8015 的固定头版本 `0c4c3d40d46d5f47d1918c905641eea969b7fa09` 与 Math-Verify 0.9.0。该 Math-Verify 包装需要显式选用，不能表述为 verl 默认训练普遍采用的路径。

专业关联拟从 AI 软件系统的结果完整性、故障可观测性和可用性展开，由任老师确认是否适合网安专业。现有证据不支持将其包装为已发现的安全漏洞。

### 实验前固定的共同条件

1. 在隔离副本中保持同一套固定版本、依赖、输入和配置，仅比较原始汇总实现与有限修复。不要把两个不同上游版本的差异全部归因于修复。
2. 复用 [现有配置](<WORKSPACE>/rewardfail/experiments/c1c_chain.py:112)：两个奖励工作进程、`rate_limited` 管理器、每个管理器默认并发上限 1；沿用库内默认 5 秒、包装外层 30 秒和管理器默认 300 秒的不同层时限，不混成一个超时参数。环境记录必须写入驱动进程与 Ray 工作进程实际导入的 `verl` 模块路径、`reward_loop.py` 路径和源文件哈希；共享环境的 editable 安装指向申请季原目录，不能只凭 `third_party` 的 git 头判断实际执行代码。
3. 复用 [现有注入机制](<WORKSPACE>/rewardfail/rewardfail/inject.py)：在指定回答附加带原始编号的标记，使判分子进程以退出码 17 退出。其余回答走原判分函数。包装器只在 `BrokenProcessPool` 时重建进程池并重试一次；台账显示同一行的实际触发次数可能是 1 次或 2 次，取决于该行首次尝试是否已被同池其他行的死亡连带。按固定包装策略核对实际注入记录：每个计划失败样本至少有 1 条台账，未计划失败的行没有台账；不预设每次重试都触发，也不以零分或报错文本代替台账。
4. 批次路径沿用真实工作进程、真实管理器、真实 `compute_rm_score` 和 `extract_reward`。生成使用既有固定回答替身，不启动模型或训练。该批次汇总函数是模块级直接调用，不代表已执行完整奖励模型部署路线。
5. 原始编号与“当前排在第几行”分开记录；重排时编号、题目、标准答案、回答及故障标记一起移动，不能重新编号。框架未承诺在奖励返回对象中携带编号时，在测试对照表中保留输入映射；不能把人工补写的编号当成框架已自动保留身份的证明。新驱动的逐样本核对表同时记录原始编号、输入位置、题目、标准答案、预期分数、实际分数和实际失败信息；重排与补齐行单独标注。
6. 原脚本仍绑定原目录，且不能完成七行截取、重排、原版对照、导出读回和独立重启。最小适配清单、隔离目录、执行前检查和命令草案见下文“实验前复核与准备”；本轮只做规划，不写新驱动、不跑实验，也不提供冒充已可运行的新命令。

### 实验二 结果读取和保存后再检查

**数据来源**：直接使用实验一七个修复后组合已经返回的结果，不再调用判分器。

**做法**：先通过真实 `extract_reward` 读取奖励与附加信息，再将对应输入、回答、标准答案、分数和附加信息交给 [现有结果导出函数 `_write_generations`](<WORKSPACE>/rewardfail/third_party/verl-pr8015/verl/trainer/ppo/ray_trainer.py:454)，写入新的 JSONL 文件，然后逐行读回。该函数会忽略长度不等于样本数的附加列，因此必须检查文件内容，不能只看“保存成功”。另做一个不调用判分器的小检查：传入一个长度等于 n+1 的附加列，确认它被忽略；再传入正常长度列，确认写入。

**看什么结果**：C0 至 C6 的文件行数、输入输出对应、分数、`error` 字段、`None` 写成 JSON `null` 后的读回值，以及错误文本是否仍存在。

**通过条件**：C0、C1、C2、C3、C4、C6 各为八行，C5 为七行；读回分数与实验一完全相同；各文件中带非空错误文本的原始样本集合仍等于计划故障集合；混合批次的正常行保留空值而不是整列被忽略，`None` 读回为 JSON `null`，错误文本仍存在；长度不符列的忽略行为有单独记录。原始编号若通过测试映射关联到文件行，要与真实输入文本交叉核对，不能靠事后改标签掩盖错位。

这项实验只验收指定读取和导出接口，不把 `None` 能保存表述为所有训练指标、损失计算或外部分析工具都能处理它。

## 开题报告初稿（2026-11-02）

本节按学院细则第六条组织：研究背景、选题依据、选题目的与意义、研究思路、研究内容、研究方法和技术路线、研究进度安排，并包含文献综述。正式开题报告的模板、篇幅、系统入口和提交方式待学院与导师确认后适配；本稿是内容初稿，不代替正式提交，也不表示开题已经通过。

### 1. 研究背景

以可验证奖励进行强化学习（RLVR）已成为提升大模型数学推理能力的主要路线之一。DeepSeekMath 提出 GRPO 等群体相对策略优化方法[1]，DeepSeek-R1[2]、Tulu 3[3]、DAPO[4] 等工作进一步说明规则化奖励在推理任务中的作用；verl/HybridFlow[5] 提供了支持多种 RL 算法的训练框架。与学习型奖励模型不同，RLVR 的奖励由可执行判分程序给出：数学任务通常解析回答与参考答案中的表达式，再用符号计算比较，Math-Verify[6] 是常用的判分库之一。二值奖励隐含一个前提：判分程序能够给出“对/错”的结论。

真实软件系统还存在第三种结果：判分未能完成。比较可能超时，解析可能抛错，执行判分的子进程可能退出，多个样本共享的进程池可能损坏。若框架把“未判定”折叠成 0 分，训练信号就无法区分“答错”和“没判出来”；若批汇总按稀疏字段拼接，失败标记还可能整列丢失或导致整批异常。随着 RLVR 训练规模扩大，判分链路的可靠性、失败信息的可观测性和结果的可复核性成为训练基础设施质量问题。本文研究这条链路上的失败信息能否被保留、被正确对应，并到达结果读取与导出。

### 2. 选题依据

（1）上游已有连续的真实故障报告。verl #5635 报告信号时限在 Ray 工作线程中无法设置，导致 MATH 奖励全零；#5839 报告禁用时限后训练挂起；#8011 报告判分子进程死亡或卡住导致持续零奖励；#8015 重建或杀死损坏的进程池，并把持续失败向上传播，使奖励管理器能够标记该行[19-22]。这些报告说明故障真实存在，但没有回答失败标记在管理器与批汇总中是否保留。

（2）稀疏元数据问题已有报告和候选修法。#6545 与 #7151 讨论奖励附加字段的稀疏问题，提出 union-key 组装与补齐缺失项；#7151 还覆盖 reward-loop、agent-loop 与全异步路径[23,24]。这说明问题类别已被认识，但缺少对特定 #8015 失败上报契约与批汇总组合的端到端追踪和独立验证。

（3）第三方审计提供了问题分类和方法参照。Rollout Cards 对 50 个仓库的失败记录做了源码审计，记录了聚合边界上的“异常转零”[18]；Where the Verifier Fails 用蜕变测试审计四类验证器，把判定分为 true、false、timeout、error、crash[11]。这些工作说明失败记录和验证器可靠性值得单独研究，但审计对象多为判分器输出或仓库整体实践，没有覆盖本文固定的 wrapper→manager→aggregation→consumer 路径。

（4）已有独立研究基础。rewardfail 仓库已在固定版本上完成真实 Ray 工作进程的两轮、13 种情形故障复现，21 个汇总契约案例，93,733 条固定回答的预声明重放（54 次库内事件、1 条零变一、18 条未裁定），193,767 条全回答扩展（2 条零变一、32 条未裁定），5,556 条第三方人工标签对照，以及自然重负载下的匹配对照。上述为历史成果，本文按导师与学院确认的范围复用，并补充真实链路上的修复验证。

（5）专业契合。本题研究软件系统的故障传播、错误可观测性与结果完整性，属于网络空间安全专业中系统可靠性与数据可信性方向的基础问题；研究结论用于改进训练基础设施的记录与验证，不主张发现新的安全漏洞。

### 3. 选题目的与意义

目的：在固定版本的 verl 与 Math-Verify 判分链路上回答三个问题：其一，判分失败信息能否穿过包装器、奖励管理器与批汇总到达奖励读取与结果导出；其二，固定回答语料在声明协议下观察到哪些时限敏感判定变化和未裁定情形；其三，时限与并发恢复策略在自然重负载输入下如何相互作用。在此基础上验证一个有界修复是否保持奖励向量、样本对应与失败标记。

意义：工程上，把失败记录从判分器扩展到消费者边界，形成可执行的回归契约，为 RL 训练框架的奖励链路提供可观测性检查点；方法上，把受控故障注入、固定语料重放和匹配对照分开使用，避免把机制、频率和诊断性批次中止混为一谈；教学上，在本科阶段完成一条真实开源框架链路的静态审计、实验设计与验证，训练可复现研究和工程分析能力。

### 4. 研究思路

以“契约”为主线：先定义判分器、包装器、管理器、批汇总与结果读取之间应满足的字段和样本对应关系；再用真实工作进程的受控故障注入定位失败信息丢失或异常的环节；随后在固定语料上测量时限敏感与未裁定情形；再用匹配的重负载对照解释超时—并发交互；最后把有界修复接入隔离副本，用七个输入组合、导出读回与独立重启复核验证修复效果和边界。历史记录与新增实验分开保存，预期结果先写定后执行，未完成和异常不省略。

### 5. 研究内容

（1）机制分析与最小复现。梳理 #8015 包装器、rate_limited 管理器、RewardLoopManager.compute_rm_score 批汇总与 extract_reward 读取路径；用两轮 13 种情形和 21 个汇总契约案例解释首行键、稀疏字段、位置效应和异常传播；每条结论对应到固定版本、输入和原始记录。

（2）固定回答测量。复用 93,733 条主测量、193,767 条扩展和 5,556 条人工标签对照，整理事件分类、时限敏感性、未裁定情形和包含关系；报告分母、抽样协议、有限样本边界和不可外推范围。

（3）重负载交互对照。复用自然重负载输入与默认、串行、单重、延长时限对照，解释库内 60 秒、外层 30 秒诊断条件下批次中止与恢复策略的交互；不追加长时限重负载路线。

（4）有界修复验证。已在隔离副本中接入 row-preserving 汇总修复，完成 C0–C6 七个真实链路组合（固定版 7 次，C1、C2 各独立重启 1 次），并补原版 C4–C6 对照 3 次，合计 12 次；检查奖励向量、失败集合、注入记录和样本位置对应；用 _write_generations 导出并逐行读回；记录全部异常和失败尝试（2 次 7 行首次尝试在生成阶段中止，已保留并说明）。

（5）复现材料与论文。整理固定版本、依赖、代表输入、运行步骤、预期结果和记录索引；完成开题、中期、论文和答辩材料。

### 6. 研究方法和技术路线

研究方法：

- 静态源码审计。固定 verl PR #8015 头版本 0c4c3d40d46d5f47d1918c905641eea969b7fa09、Math-Verify 0.9.0 与 Python 3.12.8，逐层核对路由、时限、异常和字段处理。
- 受控故障注入。在指定回答附加带原始编号的标记，使判分子进程以退出码 17 退出；使用真实 Ray 工作进程、真实管理器和真实批汇总函数执行；以注入记录核验，不以零分或报错文本代替。
- 固定语料重放。预声明抽样、时限和判定协议；主测量与扩展分开；用 Clopper–Pearson 等区间给出有限样本边界；不把较长时限当作数学真值。
- 匹配对照。默认时限、串行、单重输入和延长时限对照，隔离超时与并发恢复的影响；不把诊断条件的结果外推为默认配置发生率。
- 导出读回。用真实 extract_reward 与 _write_generations 写入新的 JSONL 文件，再逐行读回核对行数、分数、error 字段和 null 处理。
- 独立重启复核。C1、C2 各增加一次独立启动，使用新的输出目录和注入记录；不通过重复运行挑选成功结果。
- 实验为 CPU 上的小批量真实链路执行，不训练模型、不加载模型权重、不重新下载数据集。

技术路线：固定环境与版本 → 复现既有机制（两轮 13 种情形、21 个契约案例）→ 在隔离副本接入有界修复 → C0–C6 真实链路（7 次）→ extract_reward 与 _write_generations 导出读回 → C1、C2 独立重启（2 次）→ 原版 C4–C6 对照（3 次）→ 逐样本核对表与结果表 → 论文与复现材料。

每步留存：配置与版本说明、结果摘要、原始日志或异常、注入记录、逐样本核对表；异常批次保留异常，不回填成功结果。

### 8. 文献综述

以可验证奖励进行强化学习是当前大模型推理能力训练的重要路线。DeepSeekMath 提出 GRPO 等群体相对策略优化方法，把同一问题的一组回答作为相对比较的单位[1]；DeepSeek-R1 展示了规则化奖励在推理任务上的应用[2]；Tulu 3 系统总结了开放模型后训练中的可验证奖励实践[3]；DAPO 进一步讨论了大规模 RL 训练中的采样与优化策略[4]；verl/HybridFlow 则提供了支持多种 RL 算法的训练框架，并定义了奖励管理器的实现方式[5]。数学任务的判分通常依赖符号计算库，Math-Verify 把答案解析与比较封装为带时限的接口[6]。这一路线把奖励从学习型模型转移到可执行程序，但也把软件可靠性问题引入了奖励信号。

验证器并不总是可靠。Cai 等把不完美验证器建模为带假阴率和假阳率的噪声奖励通道，给出群体层面的偏差分析与修正[7]；Egashira 等注入系统性验证错误，观察到训练延迟、平台期或崩溃[8]；Plesner 等在多种子实验中报告了重采样奖励噪声下的平均性能损失，同时其不确定性区间允许更大的损失[9]；Zhang 以预注册因果对照比较代码测试套件在自然假阳性存在与否时的训练差异[10]。这些工作说明错误奖励会影响训练，但主要关注错误率或训练效果，较少追踪一次具体判分失败在软件栈中如何被记录和处理。

另一类工作直接审计验证器与训练框架。Xin 用蜕变测试审计四类验证器，把判定分为 true、false、timeout、error、crash，并进一步发现 GRPO 组内验证器错误存在相关性[11,12]；Ray 对 RLVR 验证器做模糊测试[13]；Hu 等研究重复验证器的相关感知审计与预算分配、路由[14,15]；Tian 等从可靠性优先的角度设计优势函数[16]；Pan 检查 RL 对比实验中的数据陈旧问题[17]；Masters 等的 Rollout Cards 对 50 个仓库的失败记录做源码审计，记录了聚合边界上的“异常转零”[18]。这些工作把失败记录与验证器审计提升为独立问题，但审计对象多为判分器输出或仓库整体实践，尚未对某一固定版本中 wrapper→manager→aggregation→consumer 的完整路径做端到端追踪。

训练基础设施层面的故障管理也有相关工作。Zhang 等注入训练故障并从训练曲线检测[28]；iCoder-27B 区分基础设施错误与策略错误，并对有效样本归一化[29]；Nie 等与 Yang 等分析二值奖励下组内优势的退化与偏差[30,31]。这些工作说明失败处理会影响训练信号，但主要从训练曲线或优势函数层面观察，不追踪单次判分失败在软件栈中的记录路径。

在 verl 社区，判分链路的故障已有连续报告：#5635 报告信号时限在 Ray 工作线程中无法设置导致 MATH 奖励全零，#5839 报告禁用时限后训练挂起，#8011 报告判分子进程死亡或卡住导致持续零奖励，#8015 重建或杀死损坏进程池并把持续失败向上传播，使奖励管理器能够标记该行[19-22]。此外，#6545 与 #7151 讨论奖励附加字段的稀疏元数据问题，提出 union-key 组装与补齐缺失项的方法[23,24]。TRL、OpenRLHF、Ray Train 等框架的判分路径可作横向参照[25-27]，但本文不把跨框架差异归因于单一修复。这些记录证明故障机制与候选修法已经存在；修法是否在真实管理器与批汇总中保留失败标记、是否保持样本与奖励的对应，仍缺少独立验证。

综合来看，已有研究分别回答了“验证器错误如何影响训练”“验证器输出是否可靠”“仓库层面的失败记录是否完整”，但对本文关心的问题——在一个固定版本的 RL 训练框架中，判分失败信息能否穿过包装器、奖励管理器、批汇总与结果导出，以及一个有界修复能否在真实工作进程链路上保持奖励向量与样本对应——仍缺少系统的实证验证。本文以 rewardfail 的既有复现与测量为基础，补充真实链路的修复验证、导出读回与独立重启复核，并把历史测量与新增实验分开报告。需要说明：公开材料核查截至 2026 年 10 月，本文不主张对全部相关工作的穷尽覆盖；检索与引用以本地固定版本和已核查文献为准。

### 9. 研究基础与可行性

（1）已有独立研究基础。rewardfail 是学生已完成并公开的独立研究仓库，包含固定版本的源码快照、两轮 13 种真实链路故障复现、21 个汇总契约案例、93,733 条主测量、193,767 条扩展、5,556 条人工标签对照、自然重负载对照、原始运行记录、审核记录和论文源稿。数据与原始资料已复制到本工作区，历史记录保持只读。前期研究由学生主导选题、方向和方法选择，AI 工具（Claude、Codex 等）在实现、实验执行、代码分析和写作中提供了实质帮助；毕设阶段学生需要独立掌握关键实现、实验设计与结论，并在论文和答辩中如实披露 AI 辅助。

（2）环境与数据。本机为 Apple M2 Pro、10 核、16 GiB、macOS、Python 3.12.8；固定 verl PR #8015 头版本 0c4c3d4、Math-Verify 0.9.0；OpenR1-Math-220k 固定版本[32]与第三方人工标签数据[33]已在工作区；实验在隔离副本和新输出目录进行，不污染历史记录。

（3）时间与资源。距开题约 4 周，距终稿约 5.5 个月；新增技术工作约 40–60 小时，写作与答辩准备约 40–60 小时，总计约 90–140 小时；12 次真实链路执行已于 2026-11-02 完成，实际墙钟约 8 分钟（含 Ray 启动、两次首次尝试中止与重跑），CPU-only，不加载模型、不下载数据、不使用 GPU。主要成本是驱动适配、调试和记录工时。

（4）条件与限制。已有记录支持机制分析和大样本测量；修复验证需要隔离副本与新输出目录；不要求新算法、GPU 训练、跨平台移植或全量数据重跑。有限样本边界使用 Clopper–Pearson 区间[34]，但该区间依赖独立同分布假设，本文会同时报告不满足该假设的情形。

### 11. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 环境或依赖漂移，历史结果无法直接对照 | 固定版本与锁文件；隔离副本；先记录差异，只补受影响的原版对照 |
| 实际导入的代码与记录的固定版本不一致（共享环境的 editable 安装可能指向别处） | 显式设置 `sys.path`/`PYTHONPATH`；记录驱动与工作进程实际模块路径和源文件哈希；隔离副本运行 |
| 修复接入超过约 20 小时仍无法跑通最小链路 | 汇报具体阻碍和已完成部分，重新估计或收敛该环节；不自动否定整个方向 |
| 上游 PR 状态变化（合并、改头、关闭） | 验证以固定头版本为准，不依赖 PR 是否合并；记录核对日期 |
| 预期结果与实际不符 | 保留异常和失败尝试，定位原因；不修改预期来掩盖问题 |
| 时间与课程冲突 | 开题后优先完成核心实验，写作提前启动；不扩题、不追加训练实验 |
| 结论被误读 | 明确模块级、固定版本、受控故障边界；不声称训练收益、自然故障率或跨平台可靠性 |

### 讨论时的简短回答

**到底研究什么？** 像批改作业：答错的零分和批改程序坏了留下的零分，需要有不同说明。本研究检查这份说明会不会丢，修复后是否仍与原答案对应。

**别人修过，自己的工作在哪里？** 引用上游修法，完成具体链路的解释、真实数据核对、修复适配和可复核验证。这些可以构成本科实证研究，不能把别人已做的方法当成原创。

**为什么不先训练模型？** 当前检验的是软件是否正确保留字段和样本结果，固定回答足以验证这些要求。训练收益属于另一个问题，当前不作该声称。

**默认问题少，还有什么价值？** 是否能正确记录失败，与失败在指定数据中多常见，是两个问题。前者用受控案例检验，后者照实报告，不夸大危害。

**AI 帮了多少？** 前期研究由学生主导选题、方向和方法选择；Claude、Codex 等工具对实现、实验执行、代码分析和写作有实质帮助。毕设阶段学生需要独立掌握关键实现和结论，不能声称全部手写或第三方标签由自己人工完成。

以上为学习材料，不代表学生已经掌握或完成答辩。
